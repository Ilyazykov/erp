## 1. Сглаженный числитель для Yield-метрик (Revenue/FCF/Earnings)

### Идея

Сейчас числитель Revenue/FCF/Earnings Yield считается **ступенчатой функцией**:
последнее опубликованное годовое (или TTM) значение держится константой до
публикации следующего отчёта, когда происходит мгновенный скачок.

Предлагаемая замена:

1. **Предсказать следующую (ещё не опубликованную) точку** конкретным методом
   прогнозирования — метод зависит от типа метрики (см. таблицу ниже).
2. Добавить эту предсказанную точку в набор данных как обычную точку.
3. Построить **один** натуральный кубический сплайн (`scipy.interpolate.CubicSpline`,
   `bc_type="natural"`) через **все** точки — реальные отчётные + одну предсказанную.
4. Использовать значение сплайна на каждую дату как новый, гладкий числитель.
5. Когда выходит реальный отчёт — предсказанная точка заменяется на настоящую,
   и весь сплайн (и вся производная история Yield/Z-score) пересчитывается заново.

Визуальный референс (уже реализовано и проверено для VKCO как прототип, см.
`erp_valuation/vkco_zscore_experiment.py`, колонки `revenue_yield_v2` /
`z_score_v2` / `revenue_v2_bln` в `data/vkco_zscore.csv`):
- `tmp_charts/vkco_new_logic_proposal.png` — общая идея на одном графике
- `tmp_charts/vkco_new_yield_with_revenue.png` — числитель + Yield одновременно,
  старая (ступенька) и новая (сплайн) логика side-by-side
- `tmp_charts/vkco_backtest_method*.png` (10 файлов) — честный backtest
  (без заглядывания вперёд) каждого из 10 кандидатных методов прогноза

### Честный backtest: какой метод выбирать для прогноза следующей точки

Прогнали 10 методов прогнозирования на всех тикерах с достаточной историей
(`data/annual_extra.csv`, `data/vkco_annual_revenue.csv`, `data/quarterly_ni.csv`),
честно — на каждом шаге модель видела только данные "как если бы" это было
известно на тот момент (no look-ahead), и сравнивали ошибку с фактом, когда он
появился. Метрики: MAE и MSE, нормированные на прогноз "наивным" методом
(последнее значение = прогноз) как базовую линию.

#### Итоговая сводная картина по всем типам метрик

| Тип метрики                              | Лучший метод                     |
|-------------------------------------------|-----------------------------------|
| Revenue (растущие компании)                | 5/6 (процентные, CAGR)            |
| FCF (капиталоёмкие/цикличные)              | 1 (Naive)                         |
| Earnings/net income (банки, энергетика)    | 8 (Weighted LinReg)               |

Тикеры, использованные для калибровки:
- **Revenue**: VKCO, YDEX, OZON
- **FCF**: ROSN, GMKN, PLZL (YDEX fcf исключён из финального теста — содержит
  отрицательные значения, ломает часть методов и не относится к этой тройке)
- **Earnings (net income)**: SBER, T, VTBR, IRAO — поквартальный net income
  (TTM пока не использовали, тестировали прямо на квартальных точках,
  пропуски 2022 года у SBER/VTBR из-за отсутствия отчётности исключены,
  оставшиеся кварталы переиндексированы последовательно без учёта разрыва)

#### Описание 10 методов (полные формулы — в истории чата/скриптах `/tmp/plot_vkco_*backtest*.py`, не сохранены в репозитории)

1. **Naive** — прогноз = последнее известное значение (флэт)
2. **LinReg all-years** — обычная (невзвешенная) линейная регрессия по всей истории
3. **LinReg last-5y** — линейная регрессия только по последним 5 точкам
4. **Avg abs change** — среднее абсолютное изменение за последние 5 периодов, прибавленное к последнему значению
5. **Avg growth rate** — среднее арифметическое всех годовых мультипликативных отношений (ratio), применённое к последнему значению
6. **Strict CAGR** — единый компаунд-темп роста между самой первой и самой последней точкой истории (`CAGR = (y_last/y_first)^(1/n) - 1`)
7. **Cubic spline extrapolation** — натуральный кубический сплайн через все точки, продолженный по своей кривизне на один шаг вперёд (математически некорректно для экстраполяции — стабильно худший или почти худший метод везде)
8. **Weighted LinReg** — линейная регрессия с экспоненциальными весами по давности (`weight_i = λ^(лет назад)`, изначально λ=0.75, калибровка показала оптимум ближе к 0.8-0.95 в зависимости от ряда — см. ниже)
9. **Windowed CAGR** — тот же принцип, что метод 6, но окно ограничено последними 6 годами (5 периодов) вместо всей истории
10. **Weighted growth rate** — взвешенное (по давности) среднее геометрическое годовых отношений — версия метода 5 с весами

#### Калибровка λ для метода 8 (Weighted LinReg)

Не бралось "на глаз" λ=0.75 — сделали honest backtest по сетке λ от 0.05 до 1.0
с шагом 0.001 в области оптимума:

- **VKCO (revenue)**: оптимум по MAE — λ≈0.907, но кривая ОЧЕНЬ плоская в диапазоне
  0.85–1.0 (различия в 4-м знаке после запятой = статистический шум на 10 точках).
  По MSE оптимум строго λ=1.0 (т.е. вообще не взвешивать).
- **SBER (net_income)**: похожая картина, оптимум по MAE λ≈0.80, по MSE снова λ=1.0.
- **GMKN (fcf)**: единственный ряд, где взвешивание реально помогает — оптимум
  λ≈0.6-0.7, выигрыш ~6% по MAE относительно λ=1.0. Такие ряды (хаотично
  волатильные без устойчивого тренда) — редкое исключение, где recency-weighting
  окупается сильнее.

Вывод: **фиксированное λ=0.75 не обосновано** — если метод 8 будет использоваться
в production (для Earnings/net income, где он объективно лучший), стоит либо
откалибровать λ отдельно под каждый тикер/метрику через тот же backtest-скрипт,
либо просто взять λ в диапазоне 0.8-0.9 как разумный компромисс.

### Ключевые технические детали (чтобы не переизобретать)

- Дата публикации годового отчёта за год `Y`: `date(Y + 1, 3, 1)` (везде в
  проекте — `annual_report_date()`), используется как x-координата точки в
  сплайне.
- Сплайн требует минимум ~4 точки для естественных граничных условий
  (`bc_type="natural"`); при меньшем числе точек — fallback на линейную
  интерполяцию между двумя ближайшими известными точками (см.
  `get_smoothed_annual_revenue()` в `vkco_zscore_experiment.py`).
- Сплайн строится один раз на **весь** диапазон (все реальные точки + 1
  предсказанная), а не "по кускам" — иначе будет look-ahead bias или разрыв
  на стыке истории и прогноза (мы дважды наступали на эти грабли в процессе
  разработки, см. историю чата про "заглядывание вперёд" и про "угол на
  графике").
- MAE честно считается только на прогнозах, для которых уже известен факт
  (последний "открытый" прогноз — например, 2026 год для VKCO — не участвует
  в расчёте ошибки, так как факта ещё нет).

## 2. Полный учёт всех счетов/активов (не только брокерских акций)

### Идея

Сейчас "My Portfolio" (Supabase-backed часть сайта) хранит и показывает
только брокерские сделки (акции/облигации/крипта из Snowball CSV import,
см. `supabase/functions/import-trades-csv/index.ts`). Пользователь хочет
расширить это до **полной картины личного капитала**: банковские счета,
брокерские счета, наличные, крипто-кошельки и недвижимость — по образцу
таблицы/диаграмм, которые он сейчас ведёт вручную (см. скриншоты в истории
чата от 2026-09-20).

Референс — что должно получиться:

1. **Главная таблица** (аналог первого скриншота): строки — счета/источники
   (Revolut, Wise, Банк Кипра, IBKR, Freedom24, Зираат, Райф, Сбер, Тинькофф,
   Озон-Банк, Binance, Bybit, Cryptocom, Telegram-кошелёк, Trust, Nexo, cash,
   real estate); столбцы — валюты/активы (USD, EUR, GBP, RUB, TRY, RSD, CNY,
   XAU, BTC, ETH, SOL, TON, TAO, TRX, DOGE, ...); ячейки — количество каждого
   актива на каждом счету; последний столбец — сумма счёта в USD по текущему
   курсу; последняя строка — сумма по каждому активу (в его нативных
   единицах) и её USD-эквивалент.
2. **Разбивка по классам активов** (второй скриншот): те же счета-строки,
   но столбцы — не валюты, а категории (Акции, Облигации, Вклады, Кэш,
   Золото, Крипта), в USD. Это агрегация первой таблицы: один и тот же
   счёт может держать несколько классов одновременно (например, брокерский
   счёт = Акции + Облигации).
3. **Дальнейшая детализация внутри класса** (третий/четвёртый скриншоты):
   например "Акции" разбиваются на индексы/рынки (S&P500, S&P400, S&P600,
   STOXX600, MOEX, "Акции мира"), "Облигации" — на RUB/CNY отдельно с их
   собственными под-разбивками (Вклады RUB, Облигации RUB, Облигации CNY).
4. **Донат-диаграммы** (пятый/шестой скриншоты) на нескольких уровнях
   одновременно:
   - по валюте (USD/EUR/GBP/RUB/...) для конкретного счёта или в целом
   - по счёту (Revolut/IBKR/Сбер/...) внутри группы (например "мультивалютные
     карты", "российские банки")
   - по классу актива (Акции/Облигации/Вклады/Кэш/Золото/Крипта) — и общий,
     и per-account (например у Freedom24: IBKR 85% / Freedom24 15%)
   - по под-классу (BTC/ETH/SOL/... внутри крипты; MOEX/Облигации CNY/Вклады
     внутри российских инструментов)
5. **Финальная общая диаграмма** (последний скриншот) — весь капитал
   включая недвижимость: Квартира 57%, Акции 23%, Вклады 7%, Кэш 7%,
   Крипта 3%, Золото 2%, Облигации 1%.

### Почему это не тривиальное расширение текущей схемы

- Текущая схема (`trades` → `current_holdings` → `portfolio_value_usd`)
  моделирует только "тикер + количество + цена", подходит для биржевых
  инструментов с публичной ценой (MOEX/Yahoo). Банковский счёт в конкретной
  валюте (например "USD в Revolut") — это не тикер с рыночной ценой, а
  просто денежный остаток; курс нужен только для конвертации в USD (уже
  есть `latestUsdRubRate()`/CBR в `update-market-prices`, но не остальные
  валютные пары — EUR, GBP, TRY, RSD, CNY тоже нужны).
- Недвижимость ("real estate", "Квартира") не имеет тикера и рыночной цены
  вообще — это вручную вводимая оценка стоимости, которая обновляется редко
  (не ежедневным cron, а по запросу пользователя).
- Иерархия "счёт → класс актива → под-класс" (см. п.3 выше) не выражается
  единым плоским списком тикеров — нужна отдельная классификация счетов,
  а не только тикеров (`market_prices.instrument_type` сейчас классифицирует
  ТИКЕР, а не счёт, на котором он лежит).
- Один и тот же счёт может содержать несколько валют одновременно (Revolut:
  USD+EUR+GBP+XAU) — таблица счёт×валюта нужна как отдельная сущность,
  не выводится из текущих `trades`/`market_prices` view.

  `account_balances`+курсов, аналогично тому, как сейчас `portfolio_value_usd`
  агрегируется в несколько donut-диаграмм с разными группировками.
  Многоуровневая детализация (третий/четвёртый скриншоты) — судя по всему,
  просто ещё один уровень группировки, специфичный для каждого класса
  (акции группируются по индексу, облигации — по валюте эмитента).
- Донат-диаграммы: переиспользовать существующий `mpDrawTargetDonut`
  паттерн (или более простой donut без target/Z-score логики, раз тут нет
  понятия "целевого распределения" — это просто факт, не rebalancing tool)
  для каждого среза (по валюте/по счёту/по классу/по под-классу/общий).

### Целевые (target) соотношения для всего капитала

Как и для US/RU акций (`usTargetWeightsRaw`/`ru`-эквивалент, Z-score-based
target %), пользователь хочет задавать **желаемые target-соотношения** и на
этом более высоком уровне — не только "какая акция сколько% в портфеле
акций", но и, например:
- желаемое % по классам активов в целом (Акции / Облигации / Вклады / Кэш /
  Золото / Крипта / Недвижимость)
- желаемое % по валютам (USD / EUR / RUB / CNY / ...)
- возможно, желаемое % и внутри под-классов (например, целевое соотношение
  российских vs иностранных облигаций, или целевая доля недвижимости в
  общем капитале)

Это по сути тот же паттерн, что уже есть для акций (target% + donut с
current-vs-target радиусом, см. `mpDrawTargetDonut`), только применённый к
новым уровням группировки из этого раздела. Не проектировал, где хранить эти
target-веса (по аналогии с текущими `target_weights_custom` для акций —
возможно, отдельная таблица/JSON-конфиг per-user на класс/валюту), и нужно
ли к ним тоже применять Z-score-логику или это просто статичный
пользовательский % без исторической коррекции. Инструмент "сколько купить/
продать, чтобы приблизиться к target" (уже есть для акций — z-priority pool
allocation, `mpAllocatePoolByZPriorityWithLots`/`Legacy`) тоже может иметь
смысл на этом уровне, но покупка/продажа "класса активов" (не конкретного
тикера) — абстракция, требующая отдельного продумывания (что физически
покупать, если "не хватает Облигаций" — какую конкретно облигацию?).

## 3. Ручное добавление новых купленных акций/облигаций

### Проблема

Сейчас единственный способ занести сделку в `trades` — полный CSV-импорт из
Snowball через `import-trades-csv` (см.
`supabase/functions/import-trades-csv/index.ts`), который парсит весь
брокерский экспорт разом и делает full sync (удаляет все существующие
`external_source='snowball_csv'` строки, которых нет в новом файле, см.
комментарий в коде "Full sync on every upload: this CSV is the source of
truth for this user's Snowball-sourced trades"). Это нормально для основной
массы истории, но неудобно, если пользователь **только что** купил что-то
новое и хочет увидеть это на сайте сразу, не дожидаясь следующего экспорта
из Snowball — либо для активов, которых в принципе нет в Snowball
(внеброкерская сделка, ручная покупка, что-то нестандартное).

### Хорошая новость: это не конфликтует с CSV-импортом

Full-sync delete в `import-trades-csv` фильтруется по
`external_source = 'snowball_csv'` (index.ts:152) — значит он удаляет
**только** ранее CSV-импортированные строки, и не тронет вручную добавленные
записи, если у них будет другой `external_source` (например `'manual'`).
Т.е. ручной ввод и CSV-импорт могут спокойно сосуществовать без риска, что
следующая загрузка CSV случайно затрёт то, что было добавлено руками.

### Что нужно спроектировать (черновик, не обсуждено с пользователем)

1. **UI-форма** в "My Portfolio" (index.html) — поля: тикер, дата, event
   type (buy/sell/dividend/amortisation/repayment/stock_as_dividend — те же
   типы, что уже поддерживает `trades`, см.
   `supabase/migrations/20250101000001_trades_events.sql`), quantity, price,
   currency, fee/tax (опционально). Скорее всего рядом с существующей
   секцией холдингов/загрузки CSV на вкладке "My Portfolio".
2. **Способ записи**: либо прямой `sb.from('trades').insert(...)` с фронтенда
   под RLS (`auth.uid() = user_id`, уже действует — см.
   `supabase/migrations/20250101000000_init.sql`), без Edge Function вообще
   (раз это не требует серверного парсинга CSV — просто один явный
   структурированный insert от уже аутентифицированного пользователя), либо
   отдельный лёгкий Edge Function, если понадобится server-side валидация
   сложнее, чем то, что может обеспечить RLS/CHECK-constraint.
3. **`external_id`/`external_source` для ручных записей**: нужен свой
   `external_source` (например `'manual'`) и `external_id`, который не
   пересекается с `snowball_csv`-сгенерированными id (см.
   `import-trades-csv/index.ts` — там `external_id` строится из
   `event+date+symbol+quantity+price+feeTax`, без номера строки). Для ручных
   записей проще всего — детерминированно из тех же полей (та же схема), или
   просто позволить генерироваться `gen_random_uuid()`, раз тут не нужна
   идемпотентность повторной синхронизации, как для CSV.
4. **Редактирование/удаление** ранее вручную добавленных записей — как
   минимум удаление (на случай опечатки), возможно редактирование на месте.

   удаляемы вручную через этот же UI (иначе следующий CSV-sync и ручное
   изменение будут конфликтовать за источник истины) — либо это можно и не
   разграничивать явно в UI, если исходить из того, что пользователь и так
   понимает, что CSV перезапишет любые правки к `snowball_csv`-строкам при
   следующей синхронизации.
5. **Классификация тикера в `market_prices`**: если новый тикер вообще не
   был раньше в `trades` ни у одного пользователя, `update-market-prices`

## 4. Экспорт содержимого базы данных обратно в Snowball CSV

### Идея

Обратная операция к `import-trades-csv` (см.
`supabase/functions/import-trades-csv/index.ts`): выгрузить все `trades`
текущего пользователя обратно в CSV в формате, который умеет читать
Snowball, чтобы можно было перенести накопленные в базе сделки обратно в
приложение (например, если что-то было добавлено вручную мимо CSV — см.
раздел 3 выше — и это нужно синхронизировать назад в Snowball, или для
миграции/бэкапа/смены брокерского трекера).

### Формат, который нужно воспроизвести

Snowball export header (см. комментарий в начале
`import-trades-csv/index.ts`):

```
Event,Date,Symbol,Price,Quantity,Currency,FeeTax,Exchange,NKD,FeeCurrency,DoNotAdjustCash,Note
```

Событие (`Event`) — обратное отображение от `trades.side`:

| `trades.side`        | CSV `Event`         |
|-----------------------|----------------------|
| `buy`                 | `BUY`                |
| `sell`                | `SELL`               |
| `dividend`            | `DIVIDEND`           |
| `amortisation`        | `AMORTISATION`       |
| `repayment`           | `REPAYMENT`          |
| `stock_as_dividend`   | `STOCK_AS_DIVIDEND`  |

(просто инвертировать `EVENT_TO_SIDE` из `import-trades-csv/index.ts`.)

### Что уже есть в `trades`, что нужно для round-trip

Хорошая новость: миграция `20250101000001_trades_events.sql` уже добавила
все нужные колонки для полного round-trip, кроме одной:

- `ticker` → `Symbol` ✓
- `quantity` → `Quantity` ✓
- `price` → `Price` ✓
- `trade_date` → `Date` ✓ (нужно решить формат — CSV, судя по
  `parseDate()`, ожидает `YYYY-MM-DD...`, что совпадает с Postgres `date`
  ISO-выводом по умолчанию)
- `currency` → `Currency` ✓
- `fee_tax` → `FeeTax` ✓
- `fee_currency` → `FeeCurrency` ✓
- `exchange` → `Exchange` ✓
- `nkd` → `NKD` ✓
- `note` → `Note` ✓
- **`DoNotAdjustCash` — НЕТ соответствующей колонки в `trades` вообще.**
  `import-trades-csv/index.ts` не сохраняет это поле при импорте — оно
  полностью отбрасывается. Значит экспорт не может восстановить его
  исходное значение; нужно решить, что писать в эту колонку при экспорте
  (например, всегда пустую строку/`false` как безопасный дефолт, или
  добавить отдельную колонку `do_not_adjust_cash` в `trades` заранее, если
  round-trip точности критична).

### Что нужно построить

1. Либо (а) отдельный Edge Function `export-trades-csv` (симметрично
   `import-trades-csv`) — читает `trades` под RLS текущего пользователя,
   строит CSV-текст на сервере, отдаёт как `text/csv` с заголовком
   `Content-Disposition: attachment`, либо (б) чисто фронтенд-логика
   (`sb.from('trades').select('*')` уже безопасно под RLS — юзер видит
   только свои строки — и построение CSV прямо в браузере через Blob +
   `<a download>`), без необходимости в Edge Function вообще, раз это не
   требует server-side секретов/service-role.
   - Учитывая, что парсинг CSV сознательно вынесен на сервер при ИМПОРТЕ
     (см. `import-trades-csv`'s комментарий "The browser only uploads the
     file as-is; it never parses CSV itself") — по аналогии стоит уточнить
     у пользователя, важно ли и здесь держать генерацию CSV на сервере, или
     для экспорта (в отличие от импорта) это не имеет значения, раз тут нет
     недоверенного пользовательского ввода для парсинга — только собственные
     уже сохранённые данные пользователя, отдаваемые обратно ему же.
2. UI: кнопка "Export to Snowball CSV" где-то рядом с существующей формой
   загрузки CSV на вкладке "My Portfolio" в index.html.
3. Решить: экспортировать ВСЕ `trades` (включая `external_source='manual'`,
   если раздел 3 будет реализован) в один файл, или дать выбор/фильтр по
   `external_source`.
4. `external_id`/`external_source`/`id`/`user_id`/`created_at` (внутренние
   Supabase-поля) не должны попадать в экспортируемый CSV — только колонки,
   которые реально соответствуют Snowball-формату.

## 5. Рефакторинг index.html

### Проблема

`index.html` разросся до ~2300 строк, весь JS живёт в одном inline
`<script>` теге внутри HTML-файла — нет разделения на модули/файлы, многие
функции делают слишком много одновременно (загрузка данных + расчёт +
рендер диаграммы + рендер таблицы в одной функции). Пользователь явно
отметил (2026-09-20): "ты пиздец наговнокодил, даже по функциям ничего не
разносишь" — то есть проблема не в стиле кода построчно, а в отсутствии
декомпозиции на уровне функций/модулей.

Конкретные красные флаги (по состоянию на 2026-09-20, `git log` покажет,
насколько актуально к моменту чтения):

- **`loadData()` — ~950 строк** (index.html:570-1520) — одна функция, судя
  по всему, тянет данные И рендерит множество независимых графиков/вкладок
  (ERP, Yield per Stock, US ERP, и т.д.) внутри одного тела функции с
  вложенными замыканиями. Нужно разбить на: (а) отдельные fetch/parse шаги,
  (б) отдельную функцию рендера на каждую вкладку/график, вызываемые из
  тонкого координирующего `loadData()`.
- **`mpDrawTargetDonut()` — ~290 строк** (index.html:1883-2175 в последней
  известной версии) — совмещает: расчёт donut-геометрии (theta/width/
  radial), опциональный запуск z-priority allocation, рендер HTML-таблицы
  (две разные разметки в зависимости от `opts.zPriorityAllocation`), рендер
  Plotly-диаграммы. Кандидат на разбиение минимум на 3-4 функции с чёткими
  границами (geometry-only / allocation-only / table-HTML-only / plot-only).
- **`renderChart()` — ~100 строк**, тоже смешивает несколько типов графиков
  по `id` внутри одной функции с ветвлением — вероятно, стоит разнести по
  типу графика или хотя бы вынести общие куски (layout, trace-building) в
  отдельные хелперы, которых сейчас и так несколько (`jsSeries`, `erpFill`,
  `layoutWith`) — но `renderChart` их всё равно недостаточно использует по
  сравнению со своим размером.
- **Все ~24 top-level функции + вся разметка + весь CSS живут в одном
  файле.** Никакого выделения "модуля портфеля" (`mp*` функции — их уже
  десяток: `mpEscapeHtml`, `mpFormatUsd`, `mpRenderHoldings`,
  `mpRenderCashFlows`, `mpDonutLayout`, `mpAllocatePoolByZPriorityLegacy`,
  `mpAllocatePoolByZPriorityWithLots`, `mpDrawTargetDonut`,
  `mpRenderPortfolioPies`, `mpUpdateAuthUi`) от "модуля основных
  ERP-графиков" (`renderChart`, `loadData`, `autoFitYOnXChange`, `wCny`,
  `wCnyAmplified`, ...) — всё вперемешку в одном `<script>`.
- Дублирование констант между фронтендом и Edge Function (`RU_STOCK_TICKERS`
  /`US_STOCK_TICKERS` в index.html, `TARGET_UNIVERSE_TICKERS` в
  `supabase/functions/update-market-prices/index.ts` — тот же список,
  скопирован вручную, риск разъехаться при следующем изменении).

### Что важно НЕ сломать при рефакторинге

Это сайт на GitHub Pages — статика, без build step (нет bundler/npm build в
`.github/workflows/`, судя по всей текущей архитектуре). Значит любой
рефакторинг на отдельные `.js`-файлы должен:
- либо оставаться загружаемым напрямую через `<script src="...">` (ES
  modules через `<script type="module">` тоже работают без build step на
  GitHub Pages, раз сервер отдаёт статику как есть),
- либо потребует добавления build-шага (Vite/esbuild/...) в CI, что сильно
  увеличивает сложность деплоя — **не делать без явного согласия
  пользователя**, это отдельное архитектурное решение, а не часть чистки
  кода.

Также: **обе** функции аллокации (`mpAllocatePoolByZPriorityLegacy` и
`mpAllocatePoolByZPriorityWithLots`) должны остаться при рефакторинге
байтово раздельными — пользователь явно требовал двух независимых функций
(не одной с флагом), см. историю чата про lot-aware rebalancing — не
объединять их "ради чистоты", даже если рефакторинг искушает.

## 6. Подсчёт XIRR (внутренней нормы доходности) портфеля

### Идея

Показать пользователю реальную годовую доходность его портфеля (или его
части — по тикеру/по всей "My Portfolio" вкладке), учитывающую **временную
стоимость денег** — когда именно были внесены/выведены деньги, а не просто
"сколько сейчас стоит минус сколько вложил" без учёта дат. Это стандартная
метрика (Extended Internal Rate of Return) для портфелей с нерегулярными
пополнениями/сделками — как в брокерских приложениях (Snowball, судя по
всему, тоже её считает, раз пользователь сравнивает с ним).

### Входные данные уже есть в базе

`trades` (см. `supabase/migrations/20250101000001_trades_events.sql`) уже
хранит всё нужное для XIRR: `trade_date`, `side` (buy/sell/dividend/
amortisation/repayment/stock_as_dividend), `quantity`, `price`, `currency`.
Денежный поток на каждую дату:
- `buy` → отрицательный поток (деньги ушли из кармана): `-quantity * price`
- `sell` → положительный поток: `+quantity * price`
- `dividend`, `amortisation`, `repayment` → положительный поток (деньги
  пришли, не меняя позицию, см. `cash_flows` view в
  `20250101000003_holdings_view.sql`): `+quantity` (уже хранится как
  сумма, не количество единиц — см. `cash_flows.total_amount`)
- `stock_as_dividend` → **не денежный поток** (акции вместо денег, см.
  `current_holdings` view — увеличивает `quantity`, но не является cash
  event) — не должен участвовать в XIRR как денежный поток; сам факт
  получения новых акций эффективно "бесплатно" отражается в финальной
  оценке (последний "поток" ниже).
- Финальный (последний) денежный поток на сегодняшнюю дату — это ТЕКУЩАЯ
  СТОИМОСТЬ позиции целиком (`portfolio_value_usd.value_usd`), как если бы
  всё было продано сегодня — стандартная договорённость для расчёта XIRR
  "по состоянию на сейчас".

### Что нужно построить

1. **Алгоритм XIRR**: классическая задача — найти ставку `r`, при которой
   `Σ CF_i / (1+r)^((date_i - date_0)/365) = 0`. Нет closed-form решения,
   считается численно (Newton-Raphson или бисекция) — нужно реализовать
   с нуля на JS (или найти маленькую зависимость без build step, раз сайт
   статический — см. раздел 5 про отсутствие bundler). Есть готовые
   компактные реализации (~30-50 строк), можно взять за основу логику, но
   не тянуть тяжёлую библиотеку ради одной функции.
2. **Валюта**: у портфеля сделки в разных валютах (RUB, USD, ...) — нужно
   решить, конвертировать каждый денежный поток в USD по курсу НА ДАТУ
   СДЕЛКИ (более точно, но требует исторических курсов, которых пока нет
   в БД — только `latestUsdRubRate()` "на сейчас" в
   `update-market-prices/index.ts`) или использовать текущий курс для всех
   потоков (проще, но искажает историческую доходность для RUB-номинала
   при движении курса).
3. **Уровни агрегации**: по каждому тикеру отдельно (тикер-specific XIRR),
   по всему портфелю сразу (все denежные потоки вместе, с общим финальным
   значением — суммой всех текущих позиций), возможно по классу актива
   (акции/облигации отдельно) — не решено, что показывать по умолчанию, а
   что — опционально/по клику.
4. **UI**: где показать — вероятно рядом с существующей таблицей холдингов
   (`mpRenderHoldings`) как ещё одна колонка/метрика, и/или отдельная общая
   цифра "Portfolio XIRR: X% годовых" на вкладке "My Portfolio".

### Что осталось решить перед тем, как начинать

1. Точность валютной конвертации (текущий курс для всех потоков vs
   исторический курс на дату каждой сделки) — исторический вариант требует
   либо хранить курс на каждую сделку в момент импорта (в `trades` его
   сейчас нет), либо держать таблицу исторических курсов и join'ить по дате.
2. Разные валюты сделок в одном XIRR-расчёте — конвертировать все потоки в
   единую валюту (USD?) перед вычислением, или считать XIRR отдельно по
   каждой валюте?
3. `stock_as_dividend` подтверждённо исключается из денежных потоков — но
   стоит перепроверить это с пользователем перед реализацией, раз это
   влияет на итоговое число напрямую.
4. Разместить расчёт на фронтенде (JS, простая математика, не требует
   секретов/service-role) — Edge Function тут явно не нужен, в отличие от
   CSV-парсинга.

**Ничего из этого не реализовано.** Раздел фиксирует запрос, сделанный
2026-09-20, без начала работы над ним.

## 8. Автоматический импорт баланса биткойн-кошелька (первый шаг раздела 2)

### Идея

Первый конкретный шаг к разделу 2 ("полный учёт всех счетов/активов") —
подключить биткойн-баланс автоматически, без ручного ввода суммы, через
публичный blockchain explorer API (например blockchain.info,
blockstream.info, mempool.space — все дают баланс по адресу бесплатно, без
авторизации, просто GET-запросом на публичный адрес). Пользователь явно
приоритизировал крипту (2026-09-22) как первый источник, дальше — банковские
выписки (Revolut/Wise/...), что сложнее (либо ручная загрузка CSV/PDF, либо
Open Banking API, требующий регистрации как TPP — не рассматривается в этом
шаге).

### Важное разграничение: некастодиальные кошельки vs кастодиальные биржи

Пользователь изначально хотел один универсальный UX ("ввожу адрес кошелька,
бэкенд сам подтягивает баланс и сделки") для всех крипто-источников из
таблицы в разделе 2 (Binance, Bybit, Cryptocom, Telegram Wallet, Trust). Но
это технически применимо только к **некастодиальным** (on-chain) кошелькам:

- **Некастодиальные кошельки (Trust Wallet, любой обычный BTC/ETH-адрес)**
  — у пользователя есть реальный публичный blockchain-адрес. Баланс и вся
  история транзакций по нему доступны ЛЮБОМУ через публичный blockchain
  explorer, без всякой авторизации — это по определению публичная
  информация (хотя личность владельца адреса — нет, см. следующий раздел
  про защиту). Автоматизация здесь реальна и не требует секретов от
  пользователя, кроме самого адреса.
- **Кастодиальные биржи (Binance, Bybit, Cryptocom, Telegram Wallet как
  custodial-баланс внутри Telegram)** — здесь монеты физически лежат на
  балансе биржи, а не на блокчейне под контролем пользователя. Баланс
  аккаунта — приватные данные биржи, читаемые только через персональный
  API-ключ (обычно можно выпустить в настройках биржи с правами
  "read-only", без права вывода/торговли). Это принципиально другой,
  более чувствительный тип секрета, чем публичный адрес — это по сути
  ключ доступа к аккаунту пользователя на этой бирже.

**Явное решение пользователя (2026-09-22): не хранить API-ключи бирж в
Supabase, даже с RLS-защитой** — слишком чувствительно. Для кастодиальных
бирж (Binance/Bybit/Cryptocom/Telegram Wallet) остаётся **только ручной
ввод баланса**, обновляемый пользователем вручную, как и предполагалось для
банковских счетов в разделе 2 — никакой автоматизации через API-ключи биржи
в этом проекте. Автоматизация (адрес → авто-баланс+сделки) реализуется
**только** для некастодиальных on-chain кошельков.

### Критическое требование безопасности: адрес НЕ должен светиться публично

Пользователь явно сказал: "важно не хранить адреса публично". Это меняет
архитектуру по сравнению с уже существующими таблицами:

- `market_prices` — публичные рыночные данные, читаются всеми
  (`for select using (true)`), это нормально — там нет ничего личного.
- **Адрес биткойн-кошелька — это персональная, потенциально
  деанонимизирующая информация** (публичный blockchain-адрес привязывает
  реальную личность пользователя к истории всех его транзакций, если
  адрес когда-либо утечёт). Хранить его в таблице, доступной анонимному
  `anon` key на фронтенде (как сейчас `market_prices`), недопустимо.

Правильный паттерн — тот же, что уже используется для `trades`/`portfolios`
(см. `supabase/migrations/20250101000000_init.sql`, строки ~51-61): RLS
policy `auth.uid() = user_id`, так что адрес виден только самому
пользователю, никогда — другим авторизованным пользователям или анонимным
посетителям сайта.

### Предлагаемая архитектура (черновик, не реализовано)

1. **Новая таблица** `crypto_wallets` (или переиспользовать будущую
   `account_balances` из раздела 2, если её решат делать раньше) —
   `user_id`, `address` (публичный BTC-адрес), `label` (например "Trust
   Wallet", "Cryptocom" — для UI, не обязательно), created_at. RLS: `auth.uid()
   = user_id` для select/insert/update/delete — та же политика, что у
   `trades`.
2. **Не обновлять баланс на клиенте напрямую с адресом видимым в
   network-запросах браузера** — если фронтенд сам делает
   `fetch('https://blockchain.info/...')` с адресом в URL, это ничего не
   защищает: сетевые запросы браузера видны через DevTools любому, кто
   имеет доступ к устройству пользователя (не то же самое, что "публично
   в интернете", но всё равно смысл требования пользователя — не
   раскрывать адрес почём зря). Более осторожный вариант — Edge Function
   (как `update-market-prices`), которая:
   - На daily cron (или по требованию пользователя) читает адреса всех
     пользователей из `crypto_wallets` под service-role (bypass RLS,
     аналогично тому, как `update-market-prices` читает `trades`
     cross-user только для тикеров, не для приватных данных)
     — здесь это иначе: адрес *есть* приватные данные, так что даже
     service-role чтение не должно "светить" это наружу; оно просто
     дёргает публичный blockchain API server-side, где адрес не виден
     конечному пользователю через его собственный браузерный network tab.
   - Дёргает публичный blockchain explorer API за балансом по каждому
     адресу, и опционально — за полной историей транзакций по нему (тоже
     доступна публично через тот же explorer API — большинство API отдают
     и текущий баланс, и список входящих/исходящих транзакций одним и тем
     же эндпоинтом). Пользователь хочет именно это: "на бекенде он
     добавляется к моему профилю и автоматически добавляются все сделки"
     — то есть не только текущий баланс, но и история транзакций,
     импортированная как записи, аналогичные `trades` (по духу похоже на
     то, что уже делает `import-trades-csv` для брокерских CSV, только
     источник данных — blockchain explorer API, а не CSV-файл).
   - Пишет **баланс в BTC** и, если реализовывать полную историю,
     **записи транзакций** (дата, направление, сумма) в приватные таблицы
     — но НЕ сам адрес — в общие таблицы, которую видит фронтенд. Адрес
     живёт только в приватной, RLS-защищённой `crypto_wallets` таблице и
     в серверной Edge Function, никогда не в ответе, который получает
     браузер.
3. **Цена BTC**: уже частично решено — `update-market-prices/index.ts`
   уже поддерживает крипту через Yahoo (`KNOWN_CRYPTO_TICKERS`,
   `CRYPTO_YAHOO_OVERRIDES`) для тикеров вроде BTC/ETH/XAU — можно
   переиспользовать существующий price-fetch код, просто добавить
   количество BTC (из адреса) как отдельный источник quantity, не через
   `trades`, а через этот новый `crypto_wallets` баланс.

### Что осталось решить перед тем, как начинать

1. Какой blockchain explorer API использовать (blockchain.info /
   blockstream.info / mempool.space) — сравнить лимиты запросов, надёжность,
   нужен ли API-ключ.
2. Множественные адреса на пользователя (несколько кошельков) — сразу
   поддержать список, или начать с одного адреса на пользователя?
3. Только BTC для начала, или сразу заложить ту же схему для ETH и других
   он-чейн активов (архитектурно это тот же паттерн — адрес + explorer API
   — но разные API для разных сетей)?
4. Нужно ли шифровать адрес в самой таблице (application-level encryption
   поверх RLS), или RLS-изоляции (только сам пользователь может прочитать
   свою строку через `auth.uid()`) достаточно как защиты? RLS защищает от
   других пользователей сайта и от анонимных посетителей, но не от утечки
   через сам Supabase Dashboard (доступ имеет только сам разработчик, то
   есть пользователь) — вероятно, RLS без доп. шифрования достаточно,
   учитывая, что единственный человек с доступом к Dashboard — сам
   пользователь, но стоит явно проговорить это допущение перед реализацией.

**Ничего из этого не реализовано.** Раздел фиксирует запрос, сделанный
2026-09-22, без начала работы над ним.

## 9. Импорт банковских выписок (Revolut) — реализовано 2026-09-22

### Что сделано

Пользователь передумал начинать с крипты (раздел 8) и попросил начать с
банков: "стоп, нахуй мы сейчас в крипту полезли? ... Лучше с банков начать".
Дополнительное явное требование: "в таблице для сделок должна быть пометка
— в каком банке/бирже/кошельке была совершена сделка".

Реализовано:

1. **`supabase/migrations/20250101000007_trades_account.sql`** — новая
   колонка `trades.account` (nullable text) — на каком счёте/брокере/бирже
   физически совершена сделка (например "Freedom24", "IBKR", "Тинькофф",
   "Binance"). Отличается от уже существующей `trades.exchange` (это биржа,
   на которой торгуется сам инструмент — MOEX/NASDAQ, а не счёт
   пользователя). Существующие Snowball-импортированные сделки остаются с
   `account = NULL` (по явному решению пользователя — не гадать).

2. **`supabase/migrations/20250101000008_bank_transactions.sql`** — новая
   таблица `bank_transactions` для банковских выписок (не в `trades`,
   потому что `trades` заточена под сделки с активами — тикер+количество
   +цена, а банковская трата типа "Wolt €13.82" не имеет тикера). Поля:
   `user_id`, `account`, `tx_date`, `description`, `counterparty`, `amount`
   (со знаком: минус = деньги ушли), `currency`, `category` (простая
   keyword-based категоризация — по явному решению пользователя добавить
   сразу, не откладывать), `balance_after`, `external_source`,
   `external_id`. RLS: `auth.uid() = user_id`, тот же паттерн, что у
   `trades`/`crypto_wallets`.

3. **`supabase/functions/import-revolut-statement/index.ts`** — Edge
   Function, парсит **CSV** account-statement экспорт Revolut (Profile →
   Statements → Account statement → CSV), не PDF (первая версия этой сессии
   парсила текст из PDF-выписки — переделана после того, как пользователь
   прислал реальный CSV-экспорт того же счёта: "вот! тут в csv формате можно
   получить выписку оказывается"). Формат CSV: `Type,Product,Started Date,
   Completed Date,Description,Amount,Fee,Currency,State,Balance` — один файл
   содержит вперемешку все валюты/продукты счёта (Current EUR/GBP/AED/...,
   Deposit USD/EUR — Instant Access Savings), каждый блок с собственным
   балансом от 0.
   - Только строки `State=COMPLETED` импортируются — `REVERTED` (отменённые
     карточные списания) и `PENDING` (ещё не финализированные) пропускаются.
   - Строки `Product=Deposit` (Instant Access Savings — отдельный
     процентный "конверт") исключены из импорта — по той же логике, что и
     Flexible Cash Funds: это отдельный накопительный баланс, не
     повседневная трата/доход по основному счёту.
   - Внутренние переводы ("To/From Flexible Cash Funds", "To/From Instant
     Access Savings", "Net Interest Paid to...") **импортируются как
     обычные строки** (не пропускаются) — по явному требованию
     пользователя: "мне по этим таблицам потом считать конечное значение
     счёта!!!" — если их выкинуть, сумма по `bank_transactions.amount`
     разойдётся с реальным балансом счёта. Помечены `category =
     'internal_transfer'`, чтобы их можно было легко исключить из отчётов
     по тратам позже, не трогая сами данные.
   - `account = 'Revolut'` для всех строк — валюта и так приходит отдельно
     в свою колонку `currency` из CSV, не нужно её склеивать в `account`
     (пользователь это явно поправил: "ты в одну колонку чтоль запихнуть
     хочешь?! это две разные колонки!!!").
   - Дедупликация — `upsert` на `(user_id, external_source, external_id)`,
     где `external_id = Started Date + Description + Amount + Currency`.
     `Started Date` в CSV — полный timestamp до секунды
     (`2025-10-11 01:16:36`), а не только дата, так что этот ключ
     детерминирован и устойчив к повторной/пересекающейся загрузке —
     в отличие от более ранней PDF-based версии (см. историю ниже), где
     не было времени внутри дня и пришлось городить full-replace-by-date-
     range логику. Тот подход больше не нужен и был выброшен вместе с
     PDF-парсером.
   - `Flexible Cash Funds Statement` (третий отдельный CSV, который
     пользователь тоже прислал) по-прежнему НЕ парсится этой функцией —
     BUY/SELL там сделки с фондом (актив), не трата; см. п.2 ниже.

4. **`index.html`** — секция "Import bank statement (Revolut CSV)" на
   вкладке "My Portfolio": простой `<input type="file" accept=".csv">` +
   кнопка, `file.text()` отправляется на Edge Function без клиентского
   парсинга (тот же паттерн, что и у существующего Snowball CSV-импорта).
   Ранняя PDF-версия этой сессии добавляла pdf.js через CDN для извлечения
   текста в браузере — целиком удалена вместе с PDF-парсером на сервере,
   когда выяснилось, что у Revolut есть прямой CSV-экспорт.

### Явные решения пользователя (2026-09-22)

- Импортировать **всё** движение денег, включая бытовые траты (Wolt, такси,
  аренда), а не только инвестиционные операции — "Вообще всё, включая
  бытовые траты".
- Банковские выписки хранить в **отдельной новой таблице**
  `bank_transactions`, не насиловать `trades` фейковыми тикерами вида
  `EUR_CASH` — "Новая таблица bank_transactions (Recommended)".
- Категоризация трат — добавить сразу простую keyword-based, не откладывать
  — "Сразу добавить простую категоризацию".
- Выбор blockchain explorer API (из раздела 8) пользователь явно делегировал
  — "сам решай" — выбран blockstream.info, но само внедрение отложено, пока
  не реализовано (раздел 8 остался планом).
- Формат источника — CSV, а не PDF: пользователь прислал реальный CSV-экспорт
  ("вот! тут в csv формате можно получить выписку оказывается") — вся
  PDF/pdf.js-инфраструктура, написанная в начале этой сессии, выброшена и
  заменена CSV-парсером.
- `account` и `currency` — разные колонки, не склеивать их в одну строку
  вроде "Revolut EUR" — "это две разные колонки!!! в одной "револют" в
  другой валюта". `account = 'Revolut'` для всех строк.
- Deposit-продукт (Instant Access Savings) исключается из импорта, как и
  Flexible Cash Funds — "депозит ты куда хочешь?! ... как будто их вообще
  можно в таблицу к акциям" — трактуется как отдельный накопительный
  баланс/актив, не как трату по основному счёту.
- Внутренние переводы (Flexible Cash Funds, Instant Access Savings, Net
  Interest Paid) — **импортировать, не пропускать**, чтобы сходился баланс
  счёта: "мне по этим таблицам потом считать конечное значение счёта!!!".

### Что ещё не сделано / не проверено

1. **Не протестировано на реальном Deno-рантайме** — CSV-парсер написан и
   протестирован логически (порт на голый Node.js в
   `/private/tmp/.../scratchpad/test_csv_parser.js`, прогон на вырезке из
   реального CSV пользователя показал корректный результат — фильтрация
   State, пропуск Deposit, категоризация, ISO-timestamp), но не через
   `supabase functions serve`/фактический деплой — нужно `supabase db push`
   (применить обе миграции 20250101000007/20250101000008) и деплой функции
   перед реальным использованием.
2. **Flexible Cash Funds (money-market fund) CSV по-прежнему не
   импортируется никуда** — ни в `bank_transactions` (это актив, не трата),
   ни в `trades` (пока не реализовано). Пользователь прислал и этот CSV
   тоже (`savings-statement_...csv`, отдельный формат — `Date,Description,
   Value USD,Value EUR,FX Rate,Price per share,Quantity of shares`, три
   валютных под-таблицы GBP/USD/EUR в одном файле) — если понадобится
   учитывать баланс фонда как актив портфеля, это отдельная задача
   (вероятно, отдельный импортер, пишущий в `trades` под ISIN фонда как
   тикер, а не в `bank_transactions`).
3. **Другие банки** (Wise, Банк Кипра, IBKR, Freedom24, Зираат, Райф, Сбер,
   Тинькофф, Ozon-Банк) — этот Edge Function специфичен под формат Revolut
   CSV-экспорта; каждый следующий банк потребует свой парсер (или
   расширение этого под несколько форматов, если структура окажется
   похожей) — не начато.
4. **UI не тестировался в браузере** — кнопка загрузки CSV, `fetch` на
   Edge Function — код написан по аналогии с существующим Snowball CSV-
   загрузчиком, но фактический прогон в браузере (открыть сайт,
   залогиниться, загрузить реальный CSV) не выполнялся в рамках этой сессии.
5. **Часовой пояс `tx_date`** — CSV-timestamp'ы трактуются как UTC при
   импорте (`toIsoTimestamp` в Edge Function добавляет `Z`); не
   перепроверено с пользователем, действительно ли Revolut отдаёт эти
   Started Date в UTC, а не в каком-то локальном часовом поясе — если
   окажется иначе, время в `bank_transactions.tx_date` будет сдвинуто на
   разницу поясов (сама дата/порядок транзакций всё равно останутся верными
   для дедупа, пострадает только отображаемое время суток).

**Реализовано частично** — миграции и Edge Function (CSV-версия) написаны и
логически протестированы, но не задеплоены/не проверены end-to-end.
